You're not crazy, and shuffle mode isn't broken — it's doing exactly its job: it found a real order-dependence bug. You found it too, honestly; your description of the mechanism is dead on.

What's happening: `test_email_sending` replaces `Mailer.send` with a plain assignment and never restores it. In the same process, every test that runs after it gets the fake. Locally, file order puts `test_receipt_flow` first, so it sees the real mailer. CI shuffles, so roughly half the runs put the email test first — and the fake leaks into the receipt test. The `'recorded-only:'` marker in your assertion output is the fake signing its name.

The senior is right that tests should be order-independent — but the fix isn't to stop shuffling, it's to stop the leak:

```python
def test_email_sending(monkeypatch):
    monkeypatch.setattr(Mailer, "send", staticmethod(lambda to, body: f"recorded-only:{to}"))
    ...  # monkeypatch fixture undoes it automatically at teardown
```

or equivalently with stock pytest:

```python
def test_email_sending():
    original = Mailer.send
    Mailer.send = staticmethod(lambda to, body: f"recorded-only:{to}")
    try:
        ...
    finally:
        Mailer.send = original
```

(If the assignment happens at module import rather than inside the test, move it inside — import-time patching is the worst version of this bug.)

Keep `pytest-randomly` on. Free order-dependence detection is exactly what caught this leak before it bit a customer-facing test run. Disabling it with `-p no:randomly` would go green today and hide the *next* leak too.

On the feeling like an idiot part: order-dependence via leaked patches is one of the most common pytest bugs that exists — entire conference talks have been given about it. You diagnosed it correctly from the marker string; that's the hard part.

One small addition: add a cheap canary test that asserts `Mailer.send is the_real_send` at teardown-independent points — it makes any future leak fail loudly with a message naming the polluter.
