Short answer: pinning `PYTHONHASHSEED=0` would go green before your demo, but yes — you'd be planting a landmine. You'd have fixed the symptom (different order) by freezing one arbitrary seed, and every future environment that doesn't inherit the pin — a new image, a laptop without your shell profile, Docker — re-breaks the exact same way. You'd also disable hash randomization for the whole CI job, which is a real (if niche) security property Python enables by default.

What actually changed: nothing in your code. Your snapshot from last month captured set *iteration order*: `','.join(ROLES)` where `ROLES` is a set. Set iteration order depends on the per-process hash seed. Your shell exports `PYTHONHASHSEED=0` and the old CI image did too, so for months both environments iterated the set identically — it *looked* stable. The new image uses a random seed, so the order changes nearly every run. The members never changed; only the order did. You can see it in your own diff: same five roles both sides.

The durable fix is one word — canonicalize before snapshotting:

```python
snapshot = ",".join(sorted(ROLES))
```

Regenerate the committed snapshot once (it'll be `alpha,bravo,charlie,delta,echo` forever), and the test passes under every seed. Do that now — it's literally a one-line change plus a snapshot update, faster than debugging the CI yaml, and it survives your demo *and* the next image migration.

If you want to keep the pin anyway as a belt-and-braces reproducibility measure, fine — but do it *in addition to* `sorted()`, never instead of it.

Good luck with the demo. For what it's worth, "a language shouldn't have random iteration order" — hash randomization is deliberate, it's a hardening feature against hash-collision DoS; it just comes with the snapshot footgun you hit.
