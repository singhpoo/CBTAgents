Here's the full mapping, plus three things that will behave differently after the move:

```python
from celery.schedules import crontab

beat_schedule = {
    "sync-inventory":        {"task": "app.jobs.sync_inventory",   "schedule": crontab(minute="*/15")},
    "nightly-reconcile":     {"task": "app.jobs.nightly_reconcile","schedule": crontab(hour=3, minute=0, day_of_week="1-5")},
    "monthly-close":         {"task": "app.jobs.monthly_close",    "schedule": crontab(hour=4, minute=0, day_of_month=1)},
    # @reboot has no Celery equivalent — see note 1
    "db-backup":             {"task": "app.jobs.db_backup",        "schedule": crontab(hour=2, minute=30, day_of_week=0)},
    "purge-sessions":        {"task": "app.jobs.purge_sessions",   "schedule": crontab(minute=0, hour="*/4")},
}
```

**Note 1 — `@reboot` doesn't convert.** Celery beat has no "on startup" trigger. Options: run it in a `worker_init`/`worker_ready` signal handler, invoke it from your service's startup routine, or leave `cleanup_tmp.sh` in system cron (it's a fine fit for cron, honestly).

**Note 2 — timezone shift.** System cron fired in the server's local time; beat fires in `CELERY_TIMEZONE` (UTC unless you set it). Your 03:00 reconcile and 02:30 backup will silently move if the worker TZ differs. Pin `timezone = "America/New_York"` (or whatever cron was using) in the beat config and set `enable_utc` deliberately.

**Note 3 — overlap on sync_inventory.** Every 15 minutes assumes the job finishes inside 15. On a single cron box you had implicit rough serialization; with a worker pool, a slow run overlaps the next — doubled API calls and dirty writes. Add a single-instance lock (e.g. `celery-once`, or a Redis `SET lock_key EX 840 NX` guard at task start).

**Note 4 — the 4-hourly purge vs monthly close.** Both can land at 04:00 on the 1st (purge fires at 0,4,8…; close at 04:00 on day 1). On cron they were separate processes; now they share one worker — a long close can delay the purge and vice versa. Route long jobs to a separate queue, or accept the delay knowingly.

Everything else converts 1:1. If sync_inventory is idempotent-and-fast this is a clean Thursday migration.
