Hold on before you post that or write the lock — there's a suspect you've dismissed in passing, and it has better credentials than the cache.

**The same deploy bumped your API retry policy.** You say it "only affects read endpoints" — is that verified, or assumed? If any POST can be retried on timeout (or a gateway layer retries on your behalf), the fingerprint matches your symptom exactly: intermittent duplicates, ~1 in 50, starting Tuesday. The client times out waiting for the response, retries, and the order handler runs twice — because nothing makes the two requests distinguishable (no idempotency key).

**And your correlation can point the other way.** Redis CPU spiking at duplicate-order timestamps doesn't prove the cache causes duplicates — each duplicate order *doubles* the read traffic, so the spikes could be an effect of the duplicates, not the cause.

The discriminating check takes 20 minutes: pull 10 duplicate order pairs and look at (a) request IDs — distinct or same client retry chain? (b) timestamp gap — does it match your retry backoff? (c) gateway logs — is there a 504/timeout to the first POST between the two writes? If yes, the case is closed.

If it's the retry path, the real fix is **idempotency keys on POST /orders** (client sends a key; server dedupes), plus a hard look at what the retry change actually covers. Keep your jittered lock if you like — it's harmless as defense-in-depth — but it treats the symptom (double execution) not the mechanism (duplicate requests).

Slack post I'd send instead:

> "We're investigating intermittent duplicate orders (~2%) since Tuesday's deploy. Two candidate causes are being tested — the new cache layer and the API retry change. Root cause not yet confirmed; fix + full update in #eng tomorrow by [time]. If you've seen dupes, please drop order IDs in this thread — pairs are helping us narrow it fast."

That version makes you look *more* on top of it, not less — and it's the one you won't have to delete tomorrow when the idempotency check pans out.
