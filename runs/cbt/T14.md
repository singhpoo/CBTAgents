Since Tuesday, the test suite has been contradicting what you know to be true — 9001 isn't your numbering, the fixture seeds 4100 — and being gaslit by your own pipeline is exhausting. So let's be precise about what the pipeline is *actually* doing, because it isn't lying: it's telling you exactly where it's connected, and that turns out to be the whole bug.

**Situation (the record):** `test_latest_order` asserts the API returns the fixture-seeded 4100; since Tuesday CI shows `9001 != 4100`. The CI job log prints `connecting to postgres://staging-replica/orders` — the test is reading staging. A `.env` file appeared in the repo root on the runner Tuesday (created by a manual deploy-script run) containing `TEST_DB_URL=postgres://staging-replica/orders` and a live `STRIPE_KEY`. The config loader does `cfg.update(os.environ)` **then** `cfg.update(load_dotenv())`. Staging's `latest_order_id` is moving daily (9001 → 9004) because someone is testing refund flows on it. Locally: no `.env`, green.

**Hot thoughts:** "Staging data is always garbage. Ops will take a week anyway."

**Distortions at work:** Overgeneralization — "staging is ALWAYS garbage" turns Tuesday's drift into a permanent law, and quietly redirects the search from your config to someone else's data. Mind reading/fortune telling — "ops will take a week" predicts the response of people you haven't asked, and (worth noticing) you don't need ops at all here: the file and the loader are both in your hands. And underneath runs a catastrophizing pressure — release train tonight — which is what makes "just change the 4100" feel like relief.

**Evidence for the hot thought:** The test is genuinely reading garbage data — that part is real and correctly identified.

**Evidence against:** The garbage data isn't the *bug*; it's the scenery. The loader's precedence is inverted — explicit environment variables should always beat `.env`, and yours apply `.env` last, so the leaked file silently overrides the test job's real `TEST_DB_URL`. Here's the discriminating question: if the problem were staging's data, why is local green against the same test logic? Local and CI differ in exactly one variable — the presence of that `.env`.

**Balanced thought:** "The pipeline isn't gaslighting me and staging isn't the bug. My loader applies `.env` after the environment, a deploy script dropped one on the runner Tuesday, and the test has been reading staging ever since. The fix is mine to make tonight, no ops ticket required."

**The experiment (before touching anything):** in the CI job, run `TEST_DB_URL=postgres://test-db/orders pytest -k test_latest_order` with the `.env` still present. With the current loader it will *still* hit staging — the env var loses to the file. That one run proves the precedence inversion to anyone who doubts it, including future you.

**The fix (the real one):** correct the precedence — file first, explicit environment last:

```python
def load_config():
    cfg = {}
    cfg.update(load_dotenv_values(".env") or {})   # file = defaults only
    cfg.update(os.environ)                          # explicit env always wins
    return cfg
```

Then delete the leaked `.env` from the runner, add `.env` to `.gitignore`, and log a warning whenever a `.env` entry would override an already-set variable — this failure mode becomes loud instead of silent. The test returns to the test DB and stays green regardless of staging's drift. And separately: a live `STRIPE_KEY` in a plaintext file on a shared runner is a rotation-worthy security event, not a footnote.

**Why the trap is a trap:** changing the expected value to 9001 goes green *tonight* and red the morning staging drifts to 9005 — you'd have re-coupled the test to someone else's test data while CI silently keeps reading a production-adjacent replica. It relieves the release-train feeling and schedules tomorrow's panic with a worse mystery.
