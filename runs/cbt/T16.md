But you already wrote the observation that unravels the whole thing: *same five roles, different order — I can see both strings right there in the diff.* Let's take that seriously.

**Situation (the record):** `test_permissions_snapshot` compares `','.join(ROLES)` for a 5-element set against a committed snapshot. It passed in CI for months; since last week's new base image it fails almost every run. The assertion shows both strings contain the same five roles in different order. Your shell has exported `PYTHONHASHSEED=0` for months; the old CI image also exported `PYTHONHASHSEED=0`; the new image doesn't. The code didn't change.

**Hot thoughts:** "Python is nondeterministic garbage — a language shouldn't have random iteration order. The new image must be broken."

**Distortions at work:** Emotional reasoning — it feels absurd, so it *is* broken; but the behavior is documented and deliberate: set iteration order depends on the per-process hash seed, and Python randomizes that seed by default as a security hardening (hash-collision DoS protection). Labeling — "garbage"/"broken" applied to a language and an image that are both doing exactly what they promise. Mind reading — "the new image must be broken" attributes intent or fault to an environment before checking what it actually changed — which, to your credit, you then checked: the old image's seed-0 pin is the real delta.

**Evidence for the hot thought:** The test really did pass for months and really fails now; something in the environment changed. Your confusion is earned.

**Evidence against:** The members never changed — both strings in *your own diff* contain the same five roles. A "broken image" doesn't preserve set membership while permuting order; a hash-seed change does exactly that. And the stability you trusted for months was itself the anomaly: two environments both pinned to seed 0 made iteration order *look* like a language guarantee it never was. So the question: if the language were nondeterministic garbage, why did your seed-0 machine and the old seed-0 CI agree perfectly for months?

**Balanced thought:** "Nothing is broken. My snapshot accidentally captured *iteration order*, which was stable only because every environment I used shared one pin. The new image's random seed — the Python default, deliberately — exposes that. The fix is to stop snapshotting order at all."

**The experiment (before the demo, one command):** `PYTHONHASHSEED=1 pytest -k test_permissions_snapshot` on your machine — it will fail there too, with a third different order. That's the moment "the image is broken" dies: your own laptop reproduces it with one environment variable.

**The fix (the real one):** canonicalize before snapshotting —

```python
snapshot = ",".join(sorted(ROLES))    # order becomes a property of the data, not the process
```

Regenerate the committed snapshot once (`alpha,bravo,charlie,delta,echo`, forever). It passes under every seed, on every image, on every laptop — including one with no shell profile at all. It's also *less* code than the CI pin, which makes it the faster path to your demo, not the slower one.

**Why the trap is a trap:** `export PYTHONHASHSEED=0` in the job config restores green by re-creating the coincidence — two pinned environments agreeing — while coupling the snapshot to one arbitrary seed: any environment that misses the pin re-breaks identically, and you've silently disabled hash-randomization hardening for the whole job. It relieves the demo feeling and leaves the same trap armed for the next image migration.
